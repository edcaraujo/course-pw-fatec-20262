01. Fundamentos de Segurança

Zero Trust Architecture em APIs Web

A superação do modelo obsoleto de perímetro: "Never trust, always verify".

🏰 Modelo Obsoleto: Castelo & Fosso

Assumia-se que qualquer nó dentro da rede interna (VPC) era seguro. Bastava um firewall externo na borda.

A Falha Fatal: Se um único container ou credencial for comprometido, o invasor tem trânsito livre para movimento lateral em todos os bancos e microsserviços.

🛡️ Modelo Moderno: Zero Trust (NIST SP 800-207)
  • Nunca Confie, Sempre Verifique: Toda requisição precisa provar sua identidade e direitos, mesmo originada dentro do cluster.
  • Assuma a Brecha (Assume Breach): Projete a API sob a premissa de que invasores já operam na rede.
  • Privilégio Mínimo (Least Privilege): Conceda estritamente os escopos necessários com TTLs ultracurtos.
Notas do Apresentador: Mostre que mesmo chamadas serviço-a-serviço (mTLS e Service Mesh) utilizam tokens para autenticar o contexto do usuário final que originou a transação.
01. Fundamentos de Segurança

Autenticação (AuthN) vs. Autorização (AuthZ)

A diferença fundamental entre provar identidade e obter concessão de acesso.

👤 Autenticação (AuthN) — "Quem é você?"

Verificação das credenciais apresentadas para estabelecer a identidade incontestável da entidade.

  • Validação de login e hash de senha.
  • Conferência da assinatura digital do token JWT.
  • Checagem de certificados de cliente (mTLS).
  • Código HTTP sob Falha: 401 Unauthorized
🔑 Autorização (AuthZ) — "O que você pode fazer?"

Avaliação das regras de negócio para determinar se a identidade comprovada tem o direito de executar a ação.

  • Checagem de papéis (RBAC: Admin, Editor, Viewer).
  • Inspeção de escopos granulares (articles:write).
  • Validação de posse do registro alvo (Prevenção BOLA/IDOR).
  • Código HTTP sob Falha: 403 Forbidden
Notas do Apresentador: Frisamos a confusão clássica do nome da RFC: o código 401 chama-se "Unauthorized", mas significa "Unauthenticated"! O código real de falta de autorização é o 403 Forbidden.
02. Dicotomia Arquitetural

Sessões Stateful vs. Tokens Stateless

Comparativo de trade-offs entre arquiteturas centralizadas e distribuídas.

Dimensão Arquitetural Sessão Stateful (Cookie + Session Store) Token Stateless (JWT Bearer Token)
Armazenamento de Estado Servidor (Cluster Redis / Memcached / DB). Cliente (transportado em cada cabeçalho HTTP).
Custo de I/O por Chamada Alto: Leitura obrigatória de rede para cada requisição. Zero: Verificação matemática puramente via CPU local.
Escalabilidade Horizontal Limitada pelo throughput do Session Store compartilhado. Infinita: qualquer nó ou microsserviço valida autonomamente.
Revogação Imediata Instantânea: Basta deletar a chave de sessão no Redis. Complexa: Válido até o `exp` (exige blacklist ou TTL curto).
Tamanho da Carga de Rede Mínimo (~32 bytes para o identificador da sessão). Maior (~300 bytes a 2 KB com claims e assinatura).
03. Criptografia & Hashing

Encoding vs. Criptografia vs. Hashing

Fundamentos matemáticos para proteção de credenciais e integridade.

🔤 Encoding (Base64)

NÃO É SEGURANÇA! Apenas converte bytes arbitrários em caracteres ASCII seguros para tráfego web.

Reversível instantaneamente por qualquer cliente sem segredo algum.

🔐 Criptografia (AES/RSA)

Operação matemática bidirecional focada em confidencialidade.

O texto cifrado pode ser totalmente recuperado mediante a posse da chave secreta ou privada.

⚡ Hashing (Argon2/bcrypt)

Operação matemática unidirecional de digestão irreversível.

Gera um hash único. É impossível reverter matematicamente para o texto original.

⚠️ Por que MD5 e SHA-256 são Proibidos para Senhas?

Hashes rápidos foram projetados para checar integridade de arquivos em gigabytes por segundo. Uma GPU moderna (RTX 4090) calcula mais de 20 bilhões de hashes SHA-256 por segundo, permitindo quebrar senhas fracas por força bruta em segundos!

04. JSON Web Tokens (RFC 7519)

Anatomia Estrutural do JWT

Formato compacto dividido em três segmentos Base64URL separados por pontos.

1. HEADER

Metadados sobre o token:

{
  "alg": "HS256",
  "typ": "JWT"
}

Indica o algoritmo criptográfico de assinatura e a tipagem do objeto.

2. PAYLOAD (Claims)

Afirmações sobre a entidade:

{
  "sub": "usr_104",
  "name": "Mariana",
  "role": "editor",
  "exp": 1728954000
}

Contém as claims registradas e customizadas. Não é cifrado!

3. SIGNATURE

Garantia de integridade:

HMACSHA256(
  base64Url(header) + "." +
  base64Url(payload),
  secret_key
)

Impede que terceiros adulterem as claims sem invalidar a assinatura.

04. Criptografia em JWT

Assinatura Simétrica (HS256) vs. Assimétrica (RS256)

Distribuição segura de chaves em arquiteturas monolíticas e microsserviços.

🔑 Assinatura Simétrica (HMAC SHA-256 / HS256)

O emissor e todos os validadores compartilham exatamente a mesma SECRET_KEY.

  • Vantagem: Ultrarrápida e implementação trivial.
  • Risco Crítico: Se um microsserviço que apenas valida o token tiver sua chave vazada, qualquer pessoa pode usá-la para emitir novos tokens com poderes de administrador!
🏛️ Assinatura Assimétrica (RSA / RS256 / JWKS)

Usa um par de chaves: Chave Privada para emitir; Chave Pública para validar.

  • Vantagem: O Serviço de Identidade mantém a chave privada em cofre. Todos os outros microsserviços baixam a chave pública via JWKS (RFC 7517) e apenas validam tokens.
  • Segurança: Mesmo que a chave pública vaze, ninguém consegue emitir tokens válidos!
05. Ciclo de Vida do Token

Refresh Token Rotation (RTR) & Detecção de Roubo

Como conciliar segurança de curto prazo com sessões prolongadas e detecção ativa de replay.

⏱️ Access Token (Curta Duração)

TTL típico: 5 a 15 minutos.

Enviado em toda requisição HTTP no cabeçalho Authorization: Bearer <token>.

Se interceptado, a janela temporal de exposição é minúscula.

🔄 Refresh Token com Rotação (RTR)

TTL típico: 7 a 30 dias.

Trafegado estritamente na rota de renovação (POST /auth/refresh).

A Cada Uso: O refresh token antigo é invalidado imediatamente e um novo par de tokens é emitido.

🚨 Mecanismo de Detecção de Reuso (Reuse Detection)

Se um invasor interceptou um Refresh Token antigo e tentar utilizá-lo após ele já ter sido rotacionado pelo usuário legítimo, o servidor detecta: "Token zumbi reutilizado!". O sistema dispara um alerta e revoga imediatamente toda a família de tokens, protegendo a conta e forçando novo login.

06. Controle de Acesso

Modelo RBAC (Role-Based Access Control) & Escopos

Como modelar permissões atômicas desacopladas de regras engessadas no código.

👥 Hierarquia de Papéis (Roles)

Os usuários são vinculados a funções de negócio bem definidas:

  • Viewer: Acesso somente-leitura aos recursos públicos.
  • Editor: Leitura e escrita de recursos sob sua alçada.
  • Admin: Acesso irrestrito a operações administrativas globais.
🎯 Escopos e Permissões Granulares

O código da API nunca valida papéis fixos; valida escopos de ação e recurso:

  • articles:read, articles:write
  • invoices:pay
  • users:delete
⚡ O Alerta do BOLA / IDOR (OWASP API1)

Ter o papel de "Editor" e a permissão documents:read não significa que você pode ler os documentos confidenciais de outros usuários!

O controller deve obrigatoriamente validar a posse do recurso específico: document.owner_id == current_user.id.

07. Implementação Prática

Proteção de Rotas com FastAPI & Dependencies

Código limpo, tipado e pronto para produção com injeção de dependência.

from fastapi import FastAPI, Depends, HTTPException, status
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials
import jwt

app = FastAPI(title="TaskFlow API")
security = HTTPBearer()
SECRET_KEY = "sua_chave_mestra_super_secreta"

async def get_current_user(credentials: HTTPAuthorizationCredentials = Depends(security)):
    try:
        payload = jwt.decode(credentials.credentials, SECRET_KEY, algorithms=["HS256"])
        return payload
    except jwt.ExpiredSignatureError:
        raise HTTPException(status_code=401, detail="Token expirado.")
    except jwt.PyJWTError:
        raise HTTPException(status_code=401, detail="Assinatura inválida.")

def require_permission(permission: str):
    def checker(user: dict = Depends(get_current_user)):
        user_perms = user.get("permissions", [])
        if permission not in user_perms and "*" not in user_perms:
            raise HTTPException(status_code=403, detail=f"Falta permissão: {permission}")
        return user
    return checker

@app.post("/api/v1/articles")
async def create_article(article_data: dict, user: dict = Depends(require_permission("articles:write"))):
    return {"message": "Artigo publicado!", "author": user["sub"]}
08. Engenharia de Produção

Checklist de Segurança para APIs em Produção

Auditoria técnica essencial antes de abrir endpoints para a internet.

🔒 Criptografia & Tokens
  • HTTPS / TLS 1.3 obrigatório de ponta a ponta.
  • Senhas com Argon2id ou bcrypt (Work Factor ≥ 12).
  • Comparação em tempo constante (hmac.compare_digest).
  • Access Tokens com TTL curto (≤ 15 minutos).
  • Refresh Token Rotation (RTR) com detecção de reuso ativada.
🛡️ Controle de Acesso & Infra
  • Verificação mandatória de posse de recursos contra BOLA.
  • Rate Limiting rigoroso nas rotas de autenticação (/login, /refresh).
  • Cookies protegidos com flags HttpOnly; Secure; SameSite=Strict.
  • Segredos fora do Git e gerenciados via Secrets Manager / Vault.
  • Padronização de respostas de erro seguindo a RFC 9457.
