01. Fundamentos de Infraestrutura

O Modelo em Camadas (OSI vs. TCP/IP) & Encapsulamento

Como as abstrações de rede organizam a comunicação entre nós distribuídos no planeta.

🌐 Pilha de Protocolos TCP/IP
  • Aplicação (L7): HTTP, HTTPS, WebSockets, DNS, gRPC. Foco na lógica de negócio e APIs.
  • Transporte (L4): TCP, UDP, QUIC. Gerencia portas, multiplexação e confiabilidade fim-a-fim.
  • Rede / Internet (L3): IPv4 e IPv6. Responsável pelo roteamento global de pacotes via roteadores e BGP.
  • Enlace / Física (L2/L1): Ethernet, Wi-Fi, Cabos Submarinos. Converte dados em frames e sinais elétricos/ópticos.
📦 Encapsulamento, MTU & MSS

MTU (Maximum Transmission Unit): 1500 bytes na rede Ethernet padrão.

MSS (Maximum Segment Size): Limite útil de dados TCP por pacote:

MSS = MTU (1500B) - IP Header (20B) - TCP Header (20B) = 1460 Bytes
Princípio de System Design: Payloads maiores que 1460 bytes exigem múltiplos segmentos TCP, aumentando o número de ACKs e o impacto da perda de pacotes.
Notas do Apresentador: Explique que todo dado trafegado na Web sofre encapsulamento ao descer a pilha (ganhando cabeçalhos) e desencapsulamento ao subir no destino. O MSS de 1460 bytes é um limitador físico crucial para otimização de APIs e buffers.
02. Semântica de Endereçamento

Anatomia dos Identificadores: URI vs. URL vs. URN

Compreendendo o modelo hierárquico da RFC 3986 / RFC 8141 e a anatomia exata de cada padrão.

Scheme (Protocolo): Define o protocolo de comunicação e as regras de transporte da requisição (ex: https, http, wss, ftp).
☂️ URI (Uniform Resource Identifier) • Superclasse / Identificador Global
📍 URL (Uniform Resource Locator)
"Onde está e como acessar": Identifica o recurso através do seu endereço e protocolo de transporte na rede. Se o servidor mudar de endereço, a URL quebra.
🏷️ URN (Uniform Resource Name)
"Qual é o nome persistente": Identifica o recurso por um identificador exclusivo registrado no namespace, imutável e independente de localização ou servidor.
03. Ciclo de Vida da Web (Part. 1)

A Jornada da Requisição: Parsing, Cache & DNS Hierárquico

O que acontece nos primeiros milissegundos após o usuário digitar a URL e pressionar Enter.

1️⃣ Parsing, HSTS & Caches Locais
  • HSTS Preload Check: O navegador consulta sua lista interna pré-compilada para forçar HTTPS imediatamente, prevenindo ataques de SSL Stripping.
  • Browser Cache: Verifica se a URL já possui resposta válida no Memory Cache ou Disk Cache (`Cache-Control: max-age`, `immutable`).
  • OS Cache & Hosts File: Consulta a tabela de resolução DNS do sistema operacional e o arquivo local /etc/hosts.
2️⃣ Árvore Hierárquica do DNS
  1. Recursive Resolver: Servidor DNS do ISP (ou 1.1.1.1 / 8.8.8.8) recebe a solicitação.
  2. Root Servers (.): 13 clusters mundiais que apontam para os servidores TLD.
  3. TLD Servers (.br, .com): Apontam para os Name Servers Autoritativos.
  4. Authoritative DNS: Retorna o registro final (Tipo **A** para IPv4 ou **AAAA** para IPv6) com o **TTL**.
03. Ciclo de Vida da Web (Part. 2)

A Jornada da Requisição: Roteamento BGP, TCP & TLS 1.3

Roteamento global através de Sistemas Autônomos, conexão TCP e aperto de mão criptográfico.

🌍 Roteamento BGP & CDNs

BGP (Border Gateway Protocol): Roteia pacotes através de Sistemas Autônomos (AS) globais.

Anycast CDN: A requisição atinge a borda (PoP) geograficamente mais próxima do usuário.

🤝 TCP 3-Way Handshake

Estabelece canal confiável de transporte em 1 RTT:

1. SYN (seq=X) ➔ 2. 🠔 SYN-ACK (ack=X+1) 3. ACK (seq=X+1) ➔
🔒 TLS 1.3 Handshake (1-RTT)

Negociação de chaves Diffie-Hellman Ephemeral + envio de Certificado Digital X.509 em 1 único RTT.

Suporta 0-RTT Resumption para conexões reincidentes.

03. Ciclo de Vida da Web (Part. 3)

Processamento no Backend & Critical Rendering Path

Como o servidor gera a resposta e como o navegador processa o DOM, CSSOM e pinta os pixels na tela.

⚙️ Backend & Reverse Proxy L7
  • Reverse Proxy (NGINX/Envoy): Executa SSL Termination, compressão (Brotli/Gzip) e roteia para os nós de aplicação.
  • App Server & Database: Autenticação via JWT/OAuth2, execução de regras de negócio, queries no PostgreSQL/MongoDB e cache Redis.
  • Geração do HTTP Response: Retorna status (`200 OK`), headers e payload HTML/JSON.
🎨 Critical Rendering Path no Navegador
  1. DOM Tree: Tokens HTML convertidos em nós da árvore de documentos.
  2. CSSOM Tree: Regras CSS convertidas em árvore hierárquica de estilos.
  3. Render Tree: Junção de DOM + CSSOM (ignora display: none).
  4. Layout (Reflow): Calcula a geometria, coordenadas e tamanho de cada caixa.
  5. Paint & Compositing: Desenho de pixels e envio de camadas para aceleração na GPU.

04. Camada de Transporte

Protocolos de Transporte: TCP vs. UDP

O dilema clássico da engenharia de redes: Confiabilidade absoluta vs. Velocidade e Latência mínima.

🛡️ TCP (Transmission Control Protocol)

Orientado a Conexão & Confiável (RFC 793):

  • Garantia de Entrega e Ordem: Retransmissão automática de pacotes perdidos via números de sequência e ACKs.
  • Controle de Congestionamento: Algoritmos como BBR e CUBIC modulam o tráfego evitando colapso na rede.
  • Sliding Window: Controle de fluxo para não sobrecarregar o buffer do receptor.
  • Overhead: Cabeçalho de 20 a 60 bytes + latência de handshakes.
⚡ UDP (User Datagram Protocol)

Sem Conexão & Ultraleve (RFC 768):

  • Best-Effort Delivery: "Dispare e esqueça" (Fire and forget). Sem handshakes (0ms setup time).
  • Sem Retransmissões Nativas: Se um pacote for descartado na rede, a aplicação decide se ignora ou trata.
  • Cabeçalho Mínimo: Apenas 8 bytes fixos. Mínimo overhead computacional.
  • Casos de Uso: DNS, Streaming de vídeo ao vivo (WebRTC/VoIP), Jogos Multiplayer e a base do HTTP/3 (QUIC).

05. Evolução dos Protocolos Web

Evolução do Protocolo HTTP: HTTP/1.0 a HTTP/1.1

A introdução do Keep-Alive, múltiplos domínios e o gargalo do Head-of-Line Blocking.

🕰️ HTTP/1.0 (1996)

1 Conexão TCP por Objeto:

Cada imagem, CSS ou script exigia um novo TCP Handshake completo + fechamento de conexão.

Uma página com 50 ativos realizava 50 conexões TCP isoladas, saturando os servidores web e gerando latência catastrófica.
🚀 HTTP/1.1 (1997 - RFC 2616/7230)
  • Keep-Alive: Reutilização da mesma conexão TCP para múltiplos requests sequenciais.
  • Host Header: Permitiu hospedar múltiplos domínios virtuais no mesmo endereço IP.
  • Chunked Transfer: Envio de dados em streaming sem saber o tamanho total prévio.
  • Gargalo Crítico: Head-of-Line Blocking na camada de aplicação (requisições lentas travam as subsequentes).
05. Evolução dos Protocolos Web

HTTP/2: Protocolo Binário & Multiplexação (RFC 7540)

Múltiplos streams concorrentes em uma única conexão TCP e compressão HPACK.

🗂️ Frames & Streams Binários

Substituiu mensagens em texto puro por frames binários tipados (DATA, HEADERS, SETTINGS, PING), eliminando ambiguidades sintáticas.

⚡ Multiplexação Total

Centenas de requisições e respostas trafegam intercaladas simultaneamente em uma única conexão TCP sem travar uma à outra na camada de aplicação.

📦 Compressão HPACK

Elimina a redundância de cabeçalhos repetitivos (ex: Cookies, User-Agent) através de tabelas de índices compartilhadas entre cliente e servidor.

⚠️ O Gargalo Remanescente: TCP Head-of-Line Blocking
Como todos os streams do HTTP/2 compartilham uma única fila TCP, a perda de um único pacote de qualquer stream faz com que a pilha TCP pause a entrega de TODOS os demais streams até que o pacote perdido seja retransmitido.
05. Evolução dos Protocolos Web

HTTP/3 & QUIC: O Transporte da Web Moderna sobre UDP

A superação do TCP HoL Blocking, conexão 0-RTT e migração transparente de rede (RFC 9000 / 9114).

🚀 Inovações do Protocolo QUIC
  • Construído sobre UDP: Opera no espaço de usuário, permitindo evolução rápida sem exigir atualizações no kernel dos sistemas operacionais.
  • Streams Independentes no Transporte: A perda de um pacote em um stream de imagem atrasa apenas aquela imagem; todos os outros streams (CSS, JS) continuam fluindo sem interrupção!
  • Handshake 1-RTT Unificado: Transporte e segurança TLS 1.3 são negociados em uma única troca de mensagens.
📱 Migração de Conexão (Connection ID)

No TCP tradicional, a conexão é identificada pela 4-tupla (IP Origem, Porta Origem, IP Destino, Porta Destino). Se o usuário sai do Wi-Fi e entra no 4G/5G, seu IP muda e a conexão TCP é rompida.

No QUIC / HTTP/3: A conexão é identificada por um Connection ID (CID) de 64 bits independente do IP. A troca de rede ocorre com zero interrupção para a aplicação.

06. Criptografia & Integridade

Camadas de Segurança do HTTPS & TLS 1.3

Como os pilares de criptografia simétrica, assimétrica e cadeias de certificados blindam a Web.

🔐 Confidencialidade

Criptografia Simétrica de Alta Performance: Algoritmos como AES-256-GCM ou ChaCha20-Poly1305 garantem que intermediários (Provedores, Roteadores) vejam apenas dados indecifráveis.

🛡️ Integridade dos Dados

Autenticação de Mensagens (AEAD / HMAC): Garante que nenhum byte do payload foi alterado, injetado ou corrompido durante a transmissão na rede (*Anti-Tampering*).

📜 Autenticidade & PKI

Certificados Digitais X.509: Emitidos por Autoridades Certificadoras (CAs) confiáveis. Validam a identidade do servidor e garantem que você está conectado ao domínio legítimo.

⚡ HSTS & OCSP Stapling
HSTS: Força conexões HTTPS estritas.
OCSP Stapling: O servidor anexa a prova de validade do certificado no handshake, eliminando consultas lentas do navegador à CA.
🌐 SNI & ALPN
SNI (Server Name Indication): Permite ao servidor escolher o certificado correto para múltiplos domínios no mesmo IP.
ALPN: Negocia a versão do protocolo (HTTP/2 ou HTTP/3) durante o TLS handshake.
07. Tempo Real & Streaming (Part. 1)

Modelos de Comunicação Contínua: Polling vs. SSE

A superação do ciclo Request-Response tradicional para entrega contínua de eventos do servidor.

⏱️ Short-Polling

Consulta em Intervalos Fixos: O cliente dispara requisições periódicas (ex: a cada 2s).

Altíssimo desperdício de banda e processamento com respostas 304 vazias.

⏳ Long-Polling (Comet)

Conexão Suspensa: O servidor segura a requisição HTTP aberta até ter um dado novo.

Assim que responde, a conexão é encerrada e o cliente imediatamente abre outra requisição.

📡 Server-Sent Events (SSE)

Streaming Unidirecional (Server ➔ Client): Canal HTTP contínuo (`text/event-stream`).

Suporte nativo do navegador a reconexão automática. Padrão ouro para Streaming de Respostas de IA (LLMs).

07. Tempo Real & Streaming (Part. 2)

WebSockets: Comunicação Full-Duplex Bidirecional (RFC 6455)

Canal de comunicação persistente em tempo real para jogos, mensageria e colaboração instantânea.

🔌 O Handshake de Upgrade HTTP

A conexão inicia como HTTP tradicional e migra para WebSocket:

GET /chat HTTP/1.1 Host: api.fatec.sp.gov.br Upgrade: websocket Connection: Upgrade Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ== ➔ RESPOSTA DO SERVIDOR: HTTP/1.1 101 Switching Protocols Upgrade: websocket Connection: Upgrade
⚡ Características Arquiteturais
  • Full-Duplex Real: Cliente e servidor enviam mensagens a qualquer momento de forma concorrente.
  • Overhead Mínimo: Apenas 2 a 10 bytes de cabeçalho por frame (sem headers HTTP repetitivos).
  • Estado de Conexão (Stateful): Exige gestão de instâncias de servidores, Heartbeats (Ping/Pong) e Redis Pub/Sub para escala horizontal em clusters.
  • Casos de Uso: Jogos multiplayer, edição colaborativa (Google Docs, Figma), chats e terminais remotos.
