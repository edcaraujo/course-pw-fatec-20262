01. Camadas de Alta Velocidade

Estratégias de Cache (Caching Patterns)

Como otimizar a velocidade de acesso e reduzir a carga no banco de dados principal.

⚡ Padrões de Acesso
  • Cache-Aside (Lazy Loading): A aplicação verifica o cache. Se der Cache Miss, busca no DB e popula o cache. (Ideal para leitura pesada).
  • Write-Through: A escrita salva simultaneamente no Cache e no DB. (Garante consistência).
  • Write-Back (Write-Behind): Escreve no cache e retorna rápido. O banco é atualizado assincronamente em background. (Altíssima performance de escrita).

02. Arquitetura de Renderização

Geração de Conteúdo (Rendering Patterns)

SSR vs CSR vs SSG vs ISR: O tradeoff entre performance inicial, SEO e carga no servidor.

⏱️ COMPARADOR WATERFALL DE RENDERIZAÇÃO

Server-Side Rendering (SSR)

O servidor processa a requisição, busca dados no banco e envia o HTML 100% pronto. Prós: Excelente SEO e visualização rápida (FCP). Contras: Maior tempo até o primeiro byte (TTFB).

03. Otimização de Performance

Otimização de Backend, Protocolos & Rede

Como HTTP/2, HTTP/3 (QUIC), CDNs e compressão Brotli aceleram a entrega de dados.

⚡ HTTP/2 & HTTP/3 (QUIC)
  • HTTP/2: Multiplexação de requisições na mesma conexão TCP.
  • HTTP/3 (QUIC): Opera sobre UDP, eliminando o bloqueio de cabeça de fila (Head-of-Line Blocking).
🌍 CDN (Edge Caching)

Servidores distribuídos geograficamente (Edges) que entregam ativos estáticos (HTML, imagens, JS) com latência de milissegundos.

📦 Compressão Brotli

Algoritmo de compressão superior ao Gzip, reduzindo em até 20% adicional o tamanho dos payloads de texto (HTML, CSS, JS).

04. Frontend Performance

Otimização Frontend & Critical Rendering Path

Técnicas de minificação de ativos e otimização da navegação no cliente.

✂️ Code Splitting & Tree Shaking
  • Code Splitting: Divisão do bundle JavaScript em chunks menores, carregando apenas o código da rota atual.
  • Tree Shaking: Remoção de funções e bibliotecas não utilizadas (código morto) durante a etapa de build.
🖼️ Resource Hints & Imagens Modernas
  • Formatos Modernos: WebP e AVIF com srcset e loading="lazy".
  • Resource Hints: rel="preload", rel="prefetch" e rel="preconnect" para antecipar conexões DNS/TLS.
05. Alta Disponibilidade (Part. 1)

Escalabilidade da Infraestrutura: Scale Up vs. Scale Out

O confronto arquitetural entre aumentar o hardware de um servidor ou distribuir a carga em cluster.

⬆️ Scale Up (Escalabilidade Vertical)

Conceito: Adicionar mais recursos físicos (CPU, RAM, SSDs) a um único servidor existente.

  • Vantagens: Nenhuma mudança de código ou arquitetura necessária. Latência zero de rede interna.
  • Desvantagens: Teto físico de hardware rápido; Custo exponencialmente alto; Ponto Único de Falha (SPOF); Requer tempo de inatividade (Downtime) para upgrades.
➡️ Scale Out (Escalabilidade Horizontal)

Conceito: Adicionar mais servidores idênticos (réplicas em cluster) para trabalhar em paralelo.

  • Vantagens: Escalabilidade teoricamente infinita; Alta resiliência (se 1 máquina cai, as outras assumem); Custo linear por réplica.
  • Exigências: Requer obrigatoriamente Arquitetura Stateless e um Load Balancer na frente.
05. Alta Disponibilidade (Part. 2)

Load Balancing (L4 vs. L7) & Auto Scaling

Como os balanceadores de carga distribuem tráfego e como a nuvem escala réplicas dinamicamente.

⚡ Load Balancer Layer 4 (Transporte)

Como funciona: Roteia pacotes baseado estritamente em IP e Porta TCP/UDP.

Não abre o pacote HTTP. Oferece velocidade extrema de milhões de requisições por segundo. (Ex: AWS NLB, HAProxy TCP Mode).

🧠 Load Balancer Layer 7 (Aplicação)

Como funciona: Roteia com base no conteúdo HTTP/HTTPS (URL Path, Headers, Cookies).

Permite SSL Termination, roteamento de microsserviços (/api/v1/checkout) e Sticky Sessions. (Ex: NGINX, AWS ALB).

📈 Auto Scaling (Reativo vs Preditivo)

Reativo: Adiciona servidores quando CPU > 70% por 3 min.

Preditivo: Usa aprendizado de máquina e dados históricos para escalar servidores *antes* que o pico aconteça (ex: às 17h para o rush).

06. Engenharia de Resiliência (Part. 1)

Circuit Breakers & Exponential Backoff

Protegendo o sistema contra cascatas de falhas de rede e sobrecargas de re-tentativas.

⏳ Retry com Exponential Backoff (+ Jitter)

O Problema: Quando um serviço falha temporariamente, re-tentar em intervalos fixos (ex: a cada 1s) cria o efeito Thundering Herd (manada atordoada), derrubando o servidor novamente.

A Solução: Dobrar o tempo de espera a cada tentativa mais um ruído aleatório (Jitter):

Tentativa 1: Espera 1,0s Tentativa 2: Espera 2,0s + Jitter (142ms) Tentativa 3: Espera 4,0s + Jitter (85ms) Tentativa 4: Espera 8,0s + Jitter (310ms)
06. Engenharia de Resiliência (Part. 2)

Bulkheads & Degradação Graciosa (Fallback)

Isolando falhas de componentes para garantir que serviços críticos continuem operantes.

🚢 Bulkhead (Isolamento de Recursos)

Origem do Nome: Inspirado nas anteparas estanques de um navio: se um compartimento alaga, os outros mantêm a embarcação flutuando.

Aplicação na Web: Separa pools de threads e conexões. Se a funcionalidade de Upload de Imagens sobrecarregar, a funcionalidade vital de Login e Checkout continua 100% ativa com seu próprio pool isolado.
🛡️ Degradação Graciosa (Graceful Degradation)

Conceito: Capacidade de responder em modo reduzido/simplificado (Fallback) em vez de lançar um erro HTTP 500 ao cliente.

Exemplo de E-commerce: Se o microserviço de "Recomendações via IA" cair, o sistema exibe silenciosamente uma lista estática de "Mais Populares" salvos em cache, mantendo a venda.
07. Telemetria & Operações

Os 3 Pilares da Observabilidade

Logs, Métricas e Tracing Distribuído: Saindo do "está funcionando?" para o "por que está lento?".

🔍 Os 3 Pilares
  • 1. Logs (Eventos Estruturados): Registro textual de eventos específicos ("Erro de NullPointer na linha 42"). Ferramentas: ELK Stack (Elasticsearch, Logstash, Kibana), Splunk.
  • 2. Métricas (Séries Temporais): Valores numéricos agregados no tempo para análise de tendências ("Uso de CPU está em 90%"). Ferramentas: Prometheus, Grafana, Datadog.
  • 3. Tracing Distribuído (Fluxo da Requisição): Mapeia o caminho exato e o tempo gasto por uma única requisição através de dezenas de microsserviços. Ferramentas: Jaeger, Zipkin, OpenTelemetry.

09. Application Security (Part. 1)

Defesa em Camadas & Autenticação OAuth2 / OIDC

Arquitetura Defense in Depth e os padrões de identidade e autorização federada.

🛡️ Defesa em Camadas (Defense in Depth)

Princípio: Nenhuma camada única de segurança é infalível. Aplica-se múltiplos anéis de segurança concêntricos:

  1. Rede & Perímetro: Firewalls (VPC, Subnets privadas).
  2. Aplicação & WAF: Inspeção e filtragem de pacotes HTTP.
  3. Identidade & Acesso: OAuth2 / OIDC / JWT assinado.
  4. Dados: Criptografia em trânsito (TLS 1.3) e em repouso (AES-256).
🔑 AuthN vs. AuthZ (OAuth2 / OIDC)
  • AuthN (Autenticação - "Quem é você?"): Verificação da identidade do usuário (OpenID Connect - ID Token).
  • AuthZ (Autorização - "O que você pode fazer?"): Delegação de permissões de acesso a recursos (OAuth 2.0 - Access Token / Scopes).
Fluxo OIDC: Login -> Provider (Google/Auth0) -> ID Token + Access Token -> Validação JWT no Backend
09. Application Security (Part. 2)

Rate Limiting, WAF & Proteção OWASP (SQLi / XSS)

Simulador Token Bucket, inspeção de pacotes via WAF e mitigação de vulnerabilidades.

🛡️ SIMULADOR DE RATE LIMITING (TOKEN BUCKET ALGORITHM)

Algoritmo Token Bucket

Cada requisição consome 1 Token. Se o balde esvaziar (ataques de força bruta ou DDoS), a API bloqueia com HTTP 429 Too Many Requests.

🧱 WAF (Web Application Firewall)
Inspeção de pacotes na camada 7 antes de chegarem à aplicação. Bloqueia padrões conhecidos do **OWASP Top 10** (DDoS, Botnets, Path Traversal).
💉 Proteção SQL Injection & XSS
SQLi: Uso obrigatório de Prepared Statements / Parameterized Queries.
XSS: Sanitização estrita de inputs, cabeçalho Content Security Policy (CSP) e Cookies HttpOnly + SameSite.
10. Entrega Contínua

DevOps, CI/CD & Estratégias de Deploy

Pipelines de integração contínua e estratégias de deploy sem tempo de inatividade (Zero Downtime).

🔄 Pipeline de CI/CD

Commit ➔ Lint ➔ Testes Unitários ➔ Build Docker ➔ Testes de Integração ➔ Deploy.

Garante automação total e validação do código antes da entrega em produção.

🚀 Estratégias de Deploy
  • Blue/Green: Ambiente "Blue" (versão antiga) e "Green" (versão nova). A chave do roteador vira instantaneamente.
  • Canary Release: Libera a nova versão gradualmente (1% ➔ 10% ➔ 100% dos usuários), realizando rollback automático em caso de erros.
