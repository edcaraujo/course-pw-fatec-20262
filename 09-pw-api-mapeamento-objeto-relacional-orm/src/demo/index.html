01. Fundamentos de Persistência

O Descasamento de Impedância Objeto-Relacional

O conflito teórico entre o grafo de objetos e as tabelas relacionais bidimensionais.

☕ Modelo Orientado a Objetos
  • Grafos Aninhados: Objetos possuem referências diretas e coleções em memória (user.orders[0].items).
  • Identidade por Ponteiro: Dois objetos são idênticos se ocupam o mesmo endereço de memória (a is b).
  • Herança e Polimorfismo: Classes herdam comportamentos e propriedades hierarquicamente.
  • Encapsulamento: O estado interno é protegido com modificadores privados.
🗄️ Modelo Relacional (SQL)
  • Tabelas Planas: Relações bidimensionais normalizadas (Linhas e Colunas).
  • Identidade por Chave Primária: A unicidade é determinada pelo valor escalar da PK (id = 104).
  • Álgebra Relacional: Sem herança direta; relações são resolvidas por Junções (JOIN) e Foreign Keys.
  • Acesso Ad-hoc: Qualquer query arbitrária pode projetar colunas livremente.
💡 A Missão Central do ORM

O ORM (Object-Relational Mapping) atua como a ponte bidirecional que traduz automaticamente operações de orientação a objetos em comandos SQL eficientes, gerenciando o ciclo de vida e a integridade dos dados.

02. Padrões Arquiteturais

Active Record vs. Data Mapper

A dicotomia clássica descrita por Martin Fowler no livro P of EAA.

📦 Active Record (Django, Rails, Prisma)

A entidade representa tanto a linha da tabela quanto os métodos de acesso a dados:

user = User(name="Eduardo")
user.save()  # A própria entidade grava a si mesma!
users = User.find(active=True)

Vantagem: Simplicidade e altíssima velocidade em CRUDs.

Desvantagem: Alto acoplamento; viola o princípio de responsabilidade única (SRP) e dificulta testes unitários desacoplados.

🏛️ Data Mapper (SQLAlchemy 2.0, Hibernate)

A entidade é um objeto de domínio puro, isolado da camada de banco:

user = User(name="Eduardo")
session.add(user)  # O Repositório/Sessão cuida da gravação!
await session.commit()

Vantagem: Desacoplamento total, arquitetura limpa (*Clean Architecture*) e excelente testabilidade.

Desvantagem: Maior verbosidade e curva de aprendizado inicial.

02. Padrões Arquiteturais

Unit of Work (UoW) & Dirty Checking

Como os ORMs modernos rastreiam mudanças em memória e agrupam comandos atômicos.

1. Snapshot Inicial

Ao carregar user = session.get(User, 104), a Unidade de Trabalho salva um snapshot do estado exato da entidade na memória.

2. Modificação em Memória

Você altera atributos normalmente:

user.email = "novo@fatec.br"

Nenhum comando SQL é disparado neste momento!

3. Dirty Checking no Commit

Ao chamar session.commit(), o ORM compara o estado atual com o snapshot e gera o UPDATE cirúrgico apenas para os campos alterados!

⚡ Otimização Topológica

O Unit of Work organiza automaticamente a ordem lógica das operações de banco (insere primeiro os pais para obter suas chaves estrangeiras, insere depois os filhos, e por fim executa atualizações e exclusões), evitando violações de FK acidentais.

03. Modelagem de Entidades

Estratégias de Chaves Primárias: UUIDv7 vs. Auto-Increment

O impacto da escolha da PK na segurança da API e na fragmentação de índices B-Tree.

Tipo de Chave Tamanho Segurança contra IDOR Performance no Índice B-Tree Veredito
Auto-Increment / Sequence 4 a 8 bytes (BigInt) Péssima: Vaza métricas de negócio e facilita scraping por enumeração. Ótima: Inserção sequencial (Append-only). Zero fragmentação. Legado / Tabelas internas simples.
UUIDv4 (Aleatório) 16 bytes Máxima: Impossível prever ou enumerar IDs. Terrível: Fragmenta violentamente o índice B-Tree em altas taxas de inserção. Bom para segurança, ruim para alta escrita.
UUIDv7 (Time-Ordered) 16 bytes Máxima: Aleatório nos bits finais. Excelente: Inicia com timestamp Unix; inserções ordenadas no tempo! PADRÃO OURO MODERNO!
04. O Problema de Consultas N+1

Anatomia do Problema de Consultas N+1

O gargalo mais recorrente em APIs que utilizam ORMs com carregamento preguiçoso.

🚨 O Código Inocente que Destrói a API
# 1 Query inicial
authors = session.scalars(select(Author).limit(50)).all()

# No loop de serialização JSON (Pydantic / Express):
for author in authors:
    # LAZY LOAD: Dispara 1 query para cada autor!
    print(author.books)

Resultado Real:

  • 1 query para carregar os 50 autores.
  • 50 queries extras buscando os livros de cada autor individualmente.
  • Total: 1 + 50 = 51 consultas de rede!
⭐ A Solução: Eager Loading (selectinload)
stmt = (
    select(Author)
    .options(selectinload(Author.books))
    .limit(50)
)
authors = session.scalars(stmt).all()

O ORM executa EXATAMENTE 2 queries:

  1. SELECT * FROM authors LIMIT 50;
  2. SELECT * FROM books WHERE author_id IN (1, 2, ..., 50);

O relacionamento é montado em memória com zero produto cartesiano e custo previsível!

05. Transações & ACID

Ciclo Transacional no ORM: flush() vs. commit()

A diferença vital entre sincronizar buffers de rede e persistir transações permanentemente.

🌊 session.flush()
  • Envia as instruções SQL pendentes (INSERT/UPDATE) para o buffer de conexão do SGBD.
  • Chaves geradas pelo banco (Sequences/IDs) tornam-se imediatamente acessíveis no objeto Python.
  • A transação permanece ABERTA! Outras conexões ainda não veem os dados (Isolamento ACID) e a operação pode sofrer rollback completo.
💾 session.commit()
  • Chama implicitamente o flush() se houver alterações pendentes.
  • Dispara a instrução definitiva COMMIT no banco de dados.
  • Grava os dados no Write-Ahead Log (WAL) do disco, torna as alterações visíveis para todo o sistema e libera todas as travas e locks de linha.
05. Controle de Concorrência

Concorrência de Escrita: Pessimistic vs. Optimistic Locking

Como prevenir perdas de atualização (Lost Updates) e race conditions em APIs críticas.

🔒 Pessimistic Locking (SELECT FOR UPDATE)

Assume o pior: que conflitos certamente acontecerão. Bloqueia fisicamente a linha no SGBD durante a leitura:

SELECT * FROM accounts
WHERE id = 12 FOR UPDATE;

Qualquer outra transação que tentar ler ou alterar a mesma linha é forçada a aguardar em fila até o commit.

Trade-off: Segurança determinística, mas reduz o throughput e arrisca deadlocks.

🚀 Optimistic Locking (Coluna version)

Assume que conflitos são raros. Cada registro possui um contador inteiro version:

UPDATE accounts
SET balance = 50, version = 2
WHERE id = 12 AND version = 1;

Se nenhuma linha for afetada, alguém atualizou antes! O ORM lança OptimisticLockException e a API pode retentar.

Trade-off: Sem travas de banco, altíssimo throughput de leitura.

06. Migrações Estruturais

Migrações de Esquema (Database Migrations)

Infraestrutura como Código (IaC) para evolução segura e auditável do banco.

📝 O Arquivo de Migração (Alembic)

Cada alteração de banco é um script no Git com funções reversíveis:

def upgrade() -> None:
    op.add_column('users', 
        sa.Column('phone', sa.String(20))
    )

def downgrade() -> None:
    op.drop_column('users', 'phone')

Permite avançar para a versão mais recente (upgrade head) ou reverter mudanças com falhas (downgrade -1).

🎯 Tabela de Controle de Versão

O banco de dados guarda uma tabela interna (alembic_version) contendo o hash único da migração atual:

SELECT * FROM alembic_version;
-- Resultado: 'rev_a1b2c3d4'

Impede que o mesmo script seja rodado duas vezes e sincroniza pipelines CI/CD automaticamente.

07. Implementação Prática

Arquitetura de Produção: SQLAlchemy 2.0 Assíncrono

Código limpo desacoplando consultas SQL do controlador HTTP com injeção de dependência.

# Repositório com Eager Loading defensivo contra N+1
class UserRepository:
    def __init__(self, session: AsyncSession):
        self.session = session

    async def get_by_id_with_orders(self, user_id: UUID) -> User | None:
        stmt = (
            select(User)
            .where(User.id == user_id)
            .options(selectinload(User.orders))  # Resolve N+1 em 2 queries limpas!
        )
        return await self.session.scalar(stmt)

# Rota no FastAPI com injeção de dependência da sessão assíncrona
@app.get("/api/v1/users/{user_id}", response_model=UserResponse)
async def read_user(user_id: UUID, db: AsyncSession = Depends(get_db_session)):
    repo = UserRepository(db)
    user = await repo.get_by_id_with_orders(user_id)
    if not user:
        raise HTTPException(status_code=404, detail="Usuário não encontrado.")
    return user
08. Engenharia de Produção

Zero-Downtime Migrations: O Padrão Expand & Contract

Como alterar esquemas em bancos com milhões de linhas sem travar requisições.

1. Expand (Expandir)

Adicione a nova coluna permitindo nulos:

ALTER TABLE orders
ADD COLUMN status VARCHAR(20) NULL;

Evita locks exclusivos longos. A aplicação antiga continua rodando liso.

2. Backfill (Preencher)

Preencha os dados antigos em batches pequenos em background:

UPDATE orders
SET status = 'pending'
WHERE status IS NULL
LIMIT 5000;
3. Contract (Contrair)

Após todas as linhas estarem povoadas e a nova API estiver no ar, adicione a restrição NOT NULL:

ALTER TABLE orders
ALTER COLUMN status
SET NOT NULL;
09. Antipatterns

Antipatterns Clássicos com ORMs em APIs

Os erros mais caros cometidos em desenvolvimento de backend.

🚫 Sobrecarga de Hidratação (Hydration)

Fazer select(User).all() para 50.000 linhas cria 50.000 instâncias em memória rastreadas pelo Unit of Work, consumindo centenas de MB de RAM.

Solução: Use paginação estrita (LIMIT/OFFSET) ou projeção de tuplas (select(User.id, User.name)).

🚫 Inserts em Loop Individual

Fazer for item in lista: session.add(item); session.commit() gera milhares de transações de rede individuais.

Solução: Use operações em lote (session.add_all(lista) ou bulk_insert_mappings).

10. Auditoria de Produção

Checklist de Persistência & ORM

Critérios técnicos mandatórios antes do deploy de qualquer API.

🔍 Performance & Queries
  • Prevenção de N+1 garantida com selectinload nas rotas com relacionamentos.
  • Consultas de listagem paginadas com limite máximo fixo.
  • Chaves primárias modeladas com UUIDv7 ou BigInt sequencial.
  • Connection Pool dimensionado com base nos núcleos do SGBD e pool_pre_ping=True.
🛡️ Concorrência & Schemas
  • Toda alteração de banco versionada via migrações Alembic/Prisma.
  • Migrações em tabelas grandes executadas sob o padrão Expand & Contract.
  • Operações críticas concorrentes protegidas por Optimistic Locking.
  • Gerenciamento de sessão com context managers assíncronos (Zero Connection Leaks).
