02. Fundamentos

O que é uma API? O Contrato de Integração

A fronteira padronizada para sistemas heterogêneos dialogarem sem fricção.

Uma API (Application Programming Interface) é um conjunto formal de regras, protocolos e especificações que define a comunicação entre sistemas de software independentes.

🤝 Contrato Tecnologicamente Agnóstico
O cliente (frontend Web em Vue ou app mobile em Flutter) não precisa conhecer a linguagem interna do servidor (Python, Java ou Rust), nem o modelo físico de tabelas no banco de dados.
🧩 Desacoplamento & Evolução
Provedor e consumidor evoluem em ritmos independentes, desde que a interface pública acordada no contrato permaneça estável e versionada.

04. Arquitetura de Software

Protocolos e Estilos Arquiteturais

Diferentes paradigmas de engenharia para problemas e contextos distintos.

Característica REST (HTTP/JSON) Padrão da Web SOAP (XML) GraphQL gRPC (Protobuf)
Paradigma Orientado a Recursos Orientado a Ações Orientado a Consultas/Grafo RPC (Chamada Remota)
Complexidade Baixa / Intuitiva Alta (WSDL rígido) Média Média
Formato Carga JSON, texto, binário Estritamente XML JSON Binário Protocol Buffers
Transporte HTTP/1.1, HTTP/2, HTTP/3 HTTP, SMTP, TCP HTTP Estritamente HTTP/2
Contrato Formal OpenAPI 3.0 / Swagger WSDL / XSD GraphQL Schema (SDL) Protocol Buffers (.proto)
Flexibilidade Recursos fixos via URIs Operações RPC fixas Altíssima (cliente define) Métodos RPC tipados
Cenário Ideal Web APIs Públicas e SaaS Legados bancários/governo Frontends com dados aninhados Microsserviços internos (East-West)
🌐 REST (Web APIs & SaaS)
O padrão de ouro da Web. Aproveita cache HTTP nativo, ampla interoperabilidade e total desacoplamento entre cliente e servidor.
🏛️ SOAP (Legado Corporativo)
Protocolo rigoroso com tipagem pesada em XML. Utilizado em integração entre sistemas bancários legados, governo e WS-Security.
📊 GraphQL (Frontend-Driven)
Único endpoint POST onde o cliente requisita exatamente os campos necessários, eliminando over-fetching em apps móveis complexos.
⚡ gRPC (Microsserviços)
Comunicação backend-to-backend de altíssimo throughput e baixíssima latência com payloads binários e streaming nativo sobre HTTP/2.
05. Processo de Engenharia

Code-First vs. Design-First (Spec-Driven Design)

A escolha metodológica que define a velocidade e harmonia do time de produto.

❌ Abordagem Code-First (Tradicional)

1. O time de backend programa rotas e lógica no código.

2. A documentação (Swagger) é gerada automaticamente como subproduto.

3. O frontend fica bloqueado aguardando endpoints subirem em homologação.

4. Resultado: Divergências tardias de contrato e retrabalho mútuo.

✅ Abordagem Design-First (Spec-Driven)

1. O contrato OpenAPI 3.0 é acordado e desenhado antes do código.

2. Um Mock Server simula respostas verossímeis imediatamente.

3. Frontend e Backend programam em paralelo total.

4. Resultado: O contrato atua como Fonte Única da Verdade (SSOT).

07. Fundamentos de Rede

O Protocolo HTTP / HTTPS

O meio universal de transmissão de dados estruturados na Web.

🌐 Anatomia da Mensagem HTTP

• Start-Line: Método HTTP, Path e versão do protocolo (ex: POST /api/v1/tasks HTTP/1.1).

• Headers: Metadados da requisição (Content-Type: application/json, Authorization: Bearer ...).

• Payload (Body): Dados serializados (documento JSON de criação/atualização).

🔒 Camada de Segurança HTTPS (TLS)

• Tráfego HTTP encapsulado em um túnel criptografado seguro.

• Confidencialidade: Impede interceptação de credenciais e tokens em trânsito.

• Integridade: Assegura que o pacote não foi adulterado no caminho.

08. Teoria de Roy Fielding

REST: As 6 Restrições Arquiteturais

Definidas no ano 2000 como alicerce para escalabilidade de sistemas distribuídos.

1. Cliente-Servidor
Separação de responsabilidades de UI e armazenamento.
2. Stateless
Nenhuma sessão é armazenada na memória do servidor.
3. Cacheable
Respostas declaram explicitamente permissão de cache.
4. Interface Uniforme
Padronização universal de rotas, representações e mensagens.
5. Sistema em Camadas
Transparência em relação a proxies, CDNs e balanceadores.
6. Código sob Demanda
Opcional: envio de scripts executáveis pelo servidor.
09. Escalabilidade de Sistemas

Por que a Arquitetura REST é Stateless?

Eliminando estados locais para permitir escalabilidade horizontal ilimitada.

❌ Arquitetura Stateful (Com Sessão em RAM)

• O servidor retém dados do usuário na memória do processo.

• Exige balanceamento com Sticky Sessions (afinidade de nó).

• Se o nó reiniciar ou cair, o usuário perde a sessão e é desconectado.

✅ Arquitetura REST Stateless

• Cada pacote HTTP contém todas as credenciais necessárias.

• Autenticação via JSON Web Token (JWT) no header Authorization: Bearer <token>.

• Qualquer máquina do cluster atende qualquer requisição sem dependência local.

10. Níveis de Maturidade

O Modelo de Maturidade de Richardson

Classificação da aderência prática de uma API aos conceitos REST.

  NÍVEL 3: Controles Hipermídia (HATEOAS)
  ▲ A representação retorna links dinâmicos para as próximas ações (`_links`).
  │
  NÍVEL 2: Verbos HTTP Semânticos + Códigos de Status (Padrão da Indústria)
  ▲ Uso estrito de GET, POST, PUT, DELETE e respostas 200, 201, 204, 400, 404, etc.
  │
  NÍVEL 1: Recursos Individuais
  ▲ URIs exclusivas para cada entidade (`/api/v1/tasks/123`) em vez de endpoint único.
  │
  NÍVEL 0: O Pântano do POX (The Swamp of POX)
  ■ Um único endpoint RPC (ex: `POST /apiService` trafegando comandos em JSON/XML).
11. Semântica HTTP

Métodos HTTP: Segurança & Idempotência (RFC 9110)

A previsibilidade matemática que rege o protocolo HTTP.

Método HTTP Propósito Semântico Seguro (Safe)? Idempotente? Corpo no Request?
GET Recupera a representação do recurso SIM SIM Não recomendado
POST Cria novo recurso subordinado NÃO NÃO Sim (payload do recurso)
PUT Substituição total do recurso NÃO SIM Sim (objeto completo)
PATCH Atualização parcial de atributos NÃO NÃO* Sim (campos a alterar)
DELETE Remove o recurso indicado NÃO SIM Opcional / Raro
🛡️ Método Seguro (Safe)
A operação é estritamente de leitura; não causa mutação de dados no servidor.
🔁 Idempotência
Executar a requisição 1 vez ou 100 vezes produz rigorosamente o mesmo estado final no banco de dados.
12. Tratamento de Erros

Status Codes & Problem Details: RFC 7807 ➔ RFC 9457

O padrão de erro do IETF: a moderna RFC 9457 (2023) consolidou e sucedeu a clássica RFC 7807.

🧪 Explorador Interativo de Status Codes & Problem Details (RFC 9457 / RFC 7807)
4xx Erro do Cliente
📄 Payload Gerado (application/problem+json)
🆕 Novo Modelo: Da RFC 7807 à RFC 9457 (Julho/2023)

• Transição Normativa: A RFC 9457 é o padrão oficial vigente que tornou obsoleta a RFC 7807, preservando o media-type application/problem+json.

• Campos Canônicos: type (URI), title (título estável), status (código HTTP numérico), detail (contexto da falha) e instance (URI da ocorrência).

• Padrão about:blank: Na RFC 9457, quando o erro não possuir uma URI própria de documentação, o type assume "about:blank", com significado dado pelo status HTTP.

• Extensibilidade Oficial: Formaliza o uso de membros customizados adicionais (ex: invalidParams para erros de validação de campos).

13. Carga de Dados

Formatos de Dados: JSON vs. XML

Como os dados são serializados e transferidos na camada de aplicação.

🚀 JSON (JavaScript Object Notation)
{
  "id": "9b1deb4d...",
  "title": "Configurar Docker",
  "status": "DONE",
  "tags": ["devops", "fatec"]
}

• Leveza, legibilidade direta e suporte nativo em todas as linguagens modernas.

📜 XML (Extensible Markup Language)
<task id="9b1deb4d...">
  <title>Configurar Docker</title>
  <status>DONE</status>
  <tags><tag>devops</tag></tags>
</task>

• Validação estrita de schemas com XSD e comum em integrações legadas SOAP.

14. Diretrizes de Design

Design de Recursos, Nomenclatura & URIs

A URI identifica o substantivo; o método HTTP executa a ação.

Diretriz de Design Anti-Padrão (Evitar) ❌ Padrão Recomendado RESTful ✅
Substantivos no Plural /getTask, /task/create /tasks, /projects
Sem Verbos na URL POST /tasks/delete?id=1 DELETE /tasks/1
Minúsculas e Kebab-case /projectTasks/userList /project-tasks, /user-list
Hierarquia Natural /getTasksFromProject?id=5 /projects/5/tasks
Limite de Aninhamento /orgs/1/teams/2/users/3/tasks Máx 2 níveis: /tasks?teamId=2
🧪 Validador Semântico de URIs REST
15. Padrão RESTful

Matriz Resumo de Endpoints RESTful

A convenção consolidada para coleções e recursos individuais.

Verbo HTTP Endpoint Operação Semântica Status Code Típico
GET /tasks Lista coleção paginada de tarefas 200 OK
POST /tasks Cria uma nova tarefa subordinada 201 Created (Header Location)
GET /tasks/{id} Retorna os detalhes da tarefa indicada 200 OK ou 404 Not Found
PUT /tasks/{id} Substitui integralmente o registro 200 OK
PATCH /tasks/{id} Atualização parcial (ex: status/prioridade) 200 OK
DELETE /tasks/{id} Exclui o registro especificado 204 No Content (sem corpo)
GET /projects/{id}/tasks Lista tarefas subordinadas a um projeto 200 OK
💡 Regra de Ouro RESTful: As URLs identificam o recurso no plural (/tasks) e seus identificadores específicos no path (/tasks/{id}). A intenção da operação é expressa unicamente através do método HTTP apropriado.
16. Navegação em Coleções

Design de Coleções: Paginação, Filtros e Ordenação

Garantindo alta performance e protegendo a memória do banco de dados.

📑 Envelope Paginado Padronizado
{
  "data": [ { "id": "9b1deb4d...", "title": "Modelar Banco", "status": "IN_PROGRESS" } ],
  "meta": { "page": 1, "limit": 10, "totalItems": 42, "totalPages": 5, "hasNext": true }
}
🔍 Query Parameters Semânticos

• Paginação: GET /tasks?page=2&limit=10

• Filtros: GET /tasks?status=IN_PROGRESS&priority=HIGH

• Busca: GET /tasks?q=relatorio

• Ordenação: GET /tasks?sort=-createdAt (ordem decrescente)

🏷️ Versionamento de APIs

• Recomendado (URI): https://api.taskflow.dev/v1/tasks

• Por Cabeçalho: Accept: application/vnd.taskflow.v1+json

• O versionamento por URI é explícito e previne quebras nos clientes.

18. Ferramental Moderno

A Nova Fronteira: Contratos Vivos com OpenAPI & Apidog

Transformando o contrato na espinha dorsal da engenharia de software.

📐 OpenAPI 3.0 / Swagger
Especificação formal padronizada pela Linux Foundation para definir endpoints, parâmetros, esquemas de dados e segurança.
🤖 Smart Mocking Nativo
Servidores de simulação que geram dados aleatórios com Faker.js baseados nos nomes e regras dos atributos sem backend.
📑 Documentação Interativa
Portais vivos de documentação com console "Try it Out" e exemplos de requisição gerados automaticamente em várias linguagens.
